# v0.9c — the checker runs in CI and reports where the team reads

The team-integration slice of v0.9,
and the only one that does not touch the detector.
The umbrella scopes it as:
a GitHub Action wrapping this repository's checker,
SARIF and code-host annotations as renderers over the existing diagnostic schema,
and a recorded decision on which kinds a CI run may fail a build for.

The repository has no `.github` directory at all,
so this slice creates the CI surface it then uses on itself.

Revised after review rounds 1 and 2
(`tmp/v0.9c-ci-and-serializers_v1_review.md`, `_v2_review.md`).
Round 1 found the policy sound and the execution contract missing,
and forced the structural rule below:
one analysis pass writes the schema documents to a file,
and everything downstream — annotations, SARIF, the gate —
is a pure function of that one file.
Round 2 overturned this plan's own scope call on `--base`:
it reports span-owned diagnostics rather than whole files,
because a CI run annotates someone's pull request
and a finding that predates the branch is not that author's to answer.
Round 3 pinned the span derivation to one coordinate system —
the provider diffs the two texts itself in the core's own line partition,
and git's LF-only hunk arithmetic never enters.

## What already exists, so nothing here invents it

- `to_schema` (`scripts/check_linefeeds.py:1834`)
  is the versioned document one file's diagnostics travel in,
  and its own docstring names SARIF and annotations as renderers over it.
- `--json` already emits a list of those documents,
  in `--file` mode and in the three git modes,
  so the documents file needs no new emitting surface.
- The diagnostic's `anchor` is an absolute zero-based code-point span over the whole file
  (`line_offsets`, `scripts/check_linefeeds.py:771`;
  `_line_range`, `scripts/check_linefeeds.py:1287`).
  It is not a column,
  and a renderer that copies it as one is wrong everywhere after line 1.
- Exit codes are frozen:
  `--file` and the git modes exit 1 on any `fused`/`wrap`,
  a usage error exits 64,
  and `long` never affects an exit code (ADR-0001).
  The git-mode wrapper also exits 1 on a provider failure
  (`cli/semlf/cli.py:71-76`),
  so an exit code alone cannot distinguish findings from a broken snapshot.
- `semlf` installs from PyPI (v0.8.1, without anything this plan adds)
  and from a repository checkout (ADR-0015).

## Decision to record: what fails a CI build

CI is a different reader from the editing agent,
and the difference cuts in opposite directions for the two blocking kinds.

`fused` fails the build.
It is the kind with a measured false-positive story,
and the repository's own self-hosting rule already treats it as blocking.

`wrap` annotates as a warning and does not fail, by default.
The precedent is the `--file` audit ADR-0002 retains
(`docs/decisions/0002-wrap-withdrawn-from-default-feedback.md:124-130`):
an explicitly requested whole-file review reports `wrap`,
and a CI run is exactly such a review.
`fail-on: fused,wrap` is a separate, team-owned override
that knowingly accepts `wrap`'s measured precision risk;
it claims no precedent from the hook's wrap opt-in,
whose ADRs (0002, 0017) govern visibility while keeping exit 0,
which is a different policy axis from blocking.

`long` is a note, never more.
It is advisory by construction (ADR-0001), in every reader.

This gates on less than the CLI's exit contract blocks on, deliberately,
and the inversion lives in the Action's gate over the documents file,
never in the core:
the core's exit codes stay byte-for-byte what they are.

Recorded as ADR-0024 by Task 5.

## The one-pass contract

Everything in this slice obeys one rule:
**analyze once, then render and gate from what was written.**

The analysis pass is the existing `--json`, captured to a file.
Its exit status is kept and classified, not discarded:
0 and 1 mean the documents file is authoritative
(1 may be a `wrap` the gate will choose to pass),
and any other status — or an unparsable or missing documents file —
is a hard failure of the run, never a green build.
Rendering twice from one file cannot observe two snapshots,
which closes the double-analysis race review round 1 named.

## Group 1 — the renderers

### Task 1: `semlf render` — one subcommand, two renderers

**Class:** implementation

**Files:**
- Create: `cli/semlf/render.py`
- Modify: `cli/semlf/cli.py`
- Create: `tests/test_render.py`

`semlf render (sarif|github) [DOCUMENTS.json]`,
reading the documents list from the file or stdin,
writing the rendering to stdout, exit 0 unless the input is unreadable
or not a documents list (exit 1), or the arguments are wrong (exit 64).
A renderer never analyzes and never exits on finding content,
so the frozen exit contract is untouched by construction.
No `--sarif`/`--github` flags on the checking modes:
review round 1 showed those flags force either a second analysis pass
or a core API change, and the documents file is already the seam.

- [ ] **Step 1:** `render.sarif(documents)` returning one SARIF 2.1.0 dict.
      One run; driver `semlf` with `check_linefeeds.__version__`;
      one rule per kind with its one-line description;
      `level`: `fused` error, `wrap` warning, `long` note.
      Location conversion, pinned:
      `startLine = endLine = diagnostic["line"]`,
      `startColumn = 1`,
      `endColumn = anchor.end - anchor.start + 1`,
      `run.columnKind = "unicodeCodePoints"`,
      and `run.newlineSequences` naming **every** boundary the core's
      `str.splitlines(keepends=True)` recognizes
      (`scripts/check_linefeeds.py:771-781`), CRLF listed before its prefixes:
      `\r\n`, `\n`, `\r`, `\x0b`, `\x0c`, `\x1c`, `\x1d`, `\x1e`,
      `\x85`, `\u2028`, `\u2029`.
      A SARIF consumer interprets result lines through this list,
      so an omitted boundary misplaces every finding after it.
      Absolute anchor offsets are never copied into columns.
- [ ] **Step 2:** `render.github_annotations(documents)` yielding one
      workflow command per diagnostic:
      `fused` `::error`, `wrap` `::warning`, `long` `::notice`.
      The location mapping is pinned, not implied:
      `file` is the document's `path`,
      `line` and `endLine` are the diagnostic's one-based `line`,
      `title` is `semlf: <kind>`,
      and the message is the diagnostic's `message`.
      Two escape functions with their order pinned:
      message data escapes `%`, `\r`, `\n`;
      property values (`file`, `title`) additionally escape `:` and `,`
      (the contract of actions/toolkit `escapeProperty`).
- [ ] **Step 3:** the subcommand wiring, stdin and file input,
      and `render` alone or with a wrong renderer name exiting 64.
- [ ] **Step 4:** tests.
      SARIF: a fused/wrap/long trio maps to the three levels;
      a finding **after line 1** gets `startColumn` 1 and its own line,
      with a direct assertion that no absolute offset was copied;
      an astral character, a CRLF file, a `\u2028` separator,
      and a form-feed (`\x0c`) boundary keep line and column integrity;
      an empty documents list renders a valid SARIF document with zero results.
      Annotations: filenames containing `%`, `,`, `:`, CR, LF, and non-ASCII
      survive with property and message escaping applied;
      a finding after line 1 asserts the exact decoded `file`, `line`,
      and `title` properties rather than only the command's presence;
      exactly one command line per diagnostic.

**Acceptance:** `semlf --changed --json | semlf render sarif -`
emits a SARIF document a code host ingests,
and the same pipe with `github` annotates,
with no second analysis anywhere.

## Group 2 — selection modes CI can actually use

### Task 2: a base-revision mode, and an all-tree mode

**Class:** implementation

**Files:**
- Modify: `cli/semlf/providers.py`, `cli/semlf/cli.py`
- Modify: `tests/test_git_modes.py`

Review round 1's second P0:
`--changed` compares the worktree with `HEAD`,
so a clean CI checkout of a merged PR head has no delta at all,
and no existing mode enumerates a PR against its base.

- [ ] **Step 1:** `--base REF`:
      the files changed between `merge-base(REF, HEAD)` and the worktree,
      read from the worktree,
      through the same checkable/exclude/mode gates as every git mode —
      and reported **span-owned**, not whole-file.
      A CI run annotates someone's pull request,
      and a finding that predates the branch is not that author's to answer,
      which is exactly the ownership rule
      (`.agents/rules/100-project-map.md:96-100`, ADR-0005).
      The core already does the filtering:
      `diagnose(text, path, spans)` is the hook's own path.
      The spans come from one coordinate system, the core's own.
      Git's hunk arithmetic never enters it:
      git counts LF-delimited records
      while `line_offsets` partitions on every `str.splitlines` boundary,
      so a hunk line number after a bare CR or a form feed
      selects the wrong offset.
      Instead the provider reads the base blob and the worktree text
      and diffs them itself —
      `difflib.SequenceMatcher` over the two `splitlines(keepends=True)` lists —
      taking each non-equal opcode's after-image range as changed lines
      and converting through `line_offsets` of the worktree text.
      A delete-only opcode has an empty after-image range
      and yields the zero-width boundary at its after-image offset,
      the same boundary the hook's placement logic already models
      (`scripts/check_linefeeds.py:2341-2346`).
      A new runner variant passes the spans to `diagnose`
      while the three local modes keep their whole-file behavior unchanged.
      A `REF` that does not resolve, a missing merge base,
      and a shallow clone whose history cannot reach it
      are each a `SourceError` naming the fix (`fetch-depth: 0` or a deepen),
      never an empty result.
- [ ] **Step 2:** `--all`:
      every tracked checkable file under the configured excludes,
      whole-file (there is no change to own),
      so a full-tree run does **not** inherit `--file`'s
      explicit-paths-bypass-excludes policy.
      The enumeration is pinned rather than improvised:
      `git ls-files -z -s`, whose `mode oid stage\tpath` records
      feed the same `(path, mode, oid)` gate `_selected` already applies —
      symlinks and gitlinks fall to the mode gate,
      an unmerged entry (stage other than 0) is a `SourceError`,
      a NUL-delimited hostile path stays one token,
      and a tracked file missing from the worktree is a loud read failure.
- [ ] **Step 3:** tests over real repositories:
      a PR-shaped history where `--base` finds the merge base;
      a clean checkout where `--changed` sees nothing and `--base` sees the PR;
      a file with one pre-existing finding and one finding on a changed line,
      where `--base` reports only the second;
      a finding created by deleting a newline,
      owned through the zero-width boundary the deletion leaves;
      a change after a form-feed separator,
      owned at the right offset because no LF arithmetic was involved;
      an unresolvable base names the remedy;
      `--all` respects excludes where `--file` on the same path would not,
      skips a symlink and a gitlink by mode,
      survives a newline-bearing name,
      and refuses an unmerged index loudly.

**Acceptance:** on a clean checkout of a branch,
`semlf --base origin/main --json` enumerates exactly the PR's changed files,
and reports only the diagnostics its changed lines own.

## Group 3 — the Action, and this repository using it

### Task 3: a composite Action over its own checkout

**Class:** implementation

**Files:**
- Create: `action.yml`, `scripts/ci_gate.py`
- Modify: `README.md`

Review round 1's first P0: the published 0.8.1 cannot provide any of this.
So the Action does not install from PyPI at all:
it installs the code it shipped with —
`pip install "$GITHUB_ACTION_PATH"` —
so the Action's ref *is* the checker's version
and the dogfood job exercises exactly what a consumer gets.
There is no `version` input; pinning the Action pins everything.

Inputs:

- `fail-on`: `fused` (default) or `fused,wrap`.
  `long`, alone or in a list, is refused with a message naming ADR-0001.
- `mode`: `base` (default, against the PR base) or `all`.
- `base`: the ref for `mode: base`;
  default `${{ github.event.pull_request.base.sha }}`,
  and on non-PR events the input is required —
  an event with no base gets an error naming the input,
  not a silent full-tree run.
- `sarif-file`: optional path.
  Empty (default) writes no SARIF;
  set, the Action writes the file and exposes it as the `sarif-file` output,
  and **never uploads it** —
  the pinned `upload-sarif` step and its permissions belong to the caller.

- [ ] **Step 1:** `action.yml`, the one-pass contract in shell.
      Every `run` step declares `shell: bash`.
      One variable names the one file:
      `documents="$RUNNER_TEMP/semlf.json"`,
      used by the analysis, both renderers, and the gate,
      so nothing can read a file the analysis did not write.
      Analysis runs under `set +e` to capture the exit status,
      and `set -e` is restored immediately after,
      so a renderer failure is a failed step rather than a green one.
      Statuses other than 0 and 1,
      or a missing or unparsable documents file,
      fail the step with the checker's stderr.
      Then `semlf render github < "$documents"`,
      `semlf render sarif < "$documents" > <sarif-file>` when requested,
      and `python3 "$GITHUB_ACTION_PATH/scripts/ci_gate.py" --fail-on ...`
      over `"$documents"` for the step's final status.
      A renderer failure is tested as a hard failure.
- [ ] **Step 2:** `scripts/ci_gate.py`:
      reads the documents file, validates `fail-on`,
      exits 1 iff any diagnostic's kind is in the set.
      Stdlib only, importable, unit-tested beside the renderers.
- [ ] **Step 3:** README: the inputs table and two copy-pasteable workflows —
      the annotations-only default,
      and the SARIF variant with the caller-owned upload step
      and its `security-events: write` permission spelled out.
      Both carry `fetch-depth: 0` on their checkout step,
      because `actions/checkout` fetches one commit by default
      and `mode: base` needs history that reaches the merge base;
      a workflow-shaped test proves the documented configuration succeeds
      while an unprepared shallow checkout fails with the promised remedy.

**Acceptance:** in a test PR,
a deliberately fused line is annotated on its own line and fails the Action;
a `wrap` alone annotates as a warning and passes under the default;
`fail-on: fused,wrap` fails it;
and a sabotaged checkout with an unreadable base fails the run rather than passing it green.

## Out of scope

- Publishing a new PyPI release; the Action installs from its own ref,
  so no release gates this slice.
- Uploading SARIF anywhere; writing it is the whole contract.
- GitLab/Gitea renderers.
- Any detector or exit-code change.
